当前实现策略补充（2026-11-18）
----------------------------
  - 普通模式：已校验的只读查询默认直接执行，可关闭；其余逐次悬浮窗确认。
  - “我是高级用户”默认关闭，开启前有风险确认；绿/蓝/黄等级自动执行。
  - 红级不自动执行：高级模式下等待 3 秒后允许手动确认，普通模式使用自定义等待。
  - 风险分类不是通用 shell 安全证明：未验证脚本、复杂 shell、潜在敏感读取按红色询问。
    不根据“包含 cat/getprop 等字样”将整段脚本认作只读，也不静默禁止复杂命令。
  - “只读”不代表“无敏感数据”：已知私有数据、凭据路径与 secure 设置读取另行询问。
  - 可调：普通确认等待 0—60 秒、确认超时 10—120 秒、命令超时 1—120 秒、输出 4—256 KiB。
    确认超时必须大于按钮等待；缺少所需悬浮窗权限、拒绝、超时都不执行。
  - 只读直执行不依赖悬浮窗权限；ADB UID 2000 与 ROOT/Sui UID 0 使用同一策略。
  - UserService stdout/stderr 按字节有界排空，首行进程组标识不计入用户输出。
  - CI 139 已通过原生测试、APK 构建；Flutter 契约测试因将注释中的 PID API 当调用而失败。
    本轮修复误判，并新增策略、输出边界、设置页行为测试；新验证结果单独记录。
  - 聊天插件、持久化操作记录、重连对账尚未完成；本补充不声称这些功能可用。

议题审计后的实现补充（2026-11-18，验证进行中）
------------------------------------------------
  - 对照 ExTV/rikkahub-agent #45、#107、#104 和 Shizuku #1198；议题关闭不等于 OEM 问题已解决。
  - 绑定使用独立 epoch 和 10 秒截止时间；迟到连接/握手/死亡回调不得覆盖新连接。
  - Binder 到达后还需 UserService.status 握手，核对协议、实现版本、服务实例、实际 UID。
    授权/服务 UID 与执行端 UID 分开；没有握手时执行身份保持未知。
  - 已编写应用自有 mobile-shizuku V2 插件，锁定 @opencode/plugin 2.1.1；实际 API 声明已核验。
    工具：shizuku_status、shizuku_exec、shizuku_result；仅在内置 Ubuntu 安装，不接远端服务器。
    命令参数不包含会话/调用身份；session/message/call/agent/directory 来自 Core 工具上下文。
  - 原生桥采用应用私有 filesystem Unix socket，而非早期草案的 TCP loopback。
    原生核对 peerCredentials 的真实 Android UID；0600 socket/描述文件、0700 目录、有界帧和期限。
    桥随内置服务启动/关闭；不向 LAN 监听，不向模型提供桥凭据，不改通用 shell 路由。
  - 相同上下文生成稳定操作 ID；参数/作用域不匹配返回 conflict。
    本机私有原子记录先于 IPC 执行边界提交；取消先写 tombstone，再撤销悬浮窗/发送 Binder cancel。
    UserService 也记住先到的 cancel，防止随后到达的 execute 再启动命令。
  - 去重元数据最多 4096 条，不自动驱逐；满时拒绝新操作，不因裁剪输出而重新执行。
    原生输出缓存仅保留最近 16 条；已有会话中的工具输出按原有会话存储处理。
    App 重启后的在途记录为 unknown；同服务实例可查询真实结果，不执行重放。
  - 原生命令立即关闭 stdin，持续双流排空；JSON/Binder 编码另有上限，可能早于用户字节上限截断。
  - Core Shizuku 权限动作与本机风险悬浮窗分开；Core 拒绝必须正常传播，已保存允许不绕过红级确认。
  - 本机已跑通 Node 行为/真实 socket 字节帧测试（夹具，不是 Android 特权验证）。
    已用实际 OpenCode 2.1.1 验证注册 -> 模型工具调用 -> 私有桥 -> 模型结果继续，
    调用身份来自真实 Core 上下文；模型/原生响应是隔离夹具，不是 Android 特权验证。
    可复现：python3 tool/qa/qualify_shizuku_runtime.py（须本机有 opencode2 2.1.1，结束会关闭测试服务）。
    原生编译/行为测试与 Flutter 回归交给 CI；不把夹具结果当真机结果。
  - OEM 的 LoadedApk/UserService 初始化崩溃仍属已知兼容风险；不反射调用私有 newProcess，
    不修改第三方 APK，不因命令退出非零/超时而静默重跑或切换后端。
  - 用户真机反馈：管理器授权列表没有本应用。已补“用户点启用立即 requestPermission”，
    不以缓存 granted 跳过，并把独立申请按钮放到授权状态旁。
    API_V23 和 V3_SUPPORT 显式声明；只保留“已申请/回调状态”的真实信息，不推断申请成功等于授权成功。
  - 用户要求停止追加模拟测试并直接实装：后续使用 package_only 编译安装包；
    必须明确仅构建的提交未经过整套回归，不能冒充 CI 141 已验证的 919a288。

一、结论和优先级调整
====================

优先做一个可独立验收的 Shizuku 闭环：

  设置中查看状态
    -> 用户在系统 Shizuku 流程中授权
    -> 用户单独启用 OpenCode Plus 的 Shizuku 能力
    -> 运行只读诊断命令，核实真实身份
    -> 聊天调用 Shizuku 命令工具
    -> 返回真实输出、退出状态和耗时
    -> 支持停止、断连、重连和未确认结果查询。

Shizuku 从原总方案 S4B 中独立出来，优先级提升到第一交付批次。
它不依赖 S4A 无障碍服务、截图、通知监听或完整工作流系统。

最小依赖顺序：
  协议及生命周期约定
    -> 官方 SDK、Provider、状态与授权
    -> UserService、命令执行和取消
    -> 最小设备操作代理
    -> OpenCode V2 插件、聊天过程显示
    -> 真机验收。

原 RA-011 应拆成独立的 Shizuku Epic；键盘功能继续留在其他任务。
原 RA-010 Accessibility 不再是 Shizuku 的前置条件。

本方案以实现所需的最小底座为限，不等待总方案中全部设备工具框架完成。
协议保留后续扩展位置，但不提前实现 55 个工具组、工作流或远端设备中继。


二、首版范围
============

2.1 首版完成项

  A. 设置页
     - Shizuku 管理器安装状态。
     - Binder 是否可达、服务版本和兼容状态。
     - 应用授权状态和独立的功能启用状态。
     - 当前身份：ADB / ROOT / 未知。
     - UserService 连接状态。
     - 官方安装说明入口、打开管理器、申请授权、刷新。
     - 只读诊断、运行状态、停止当前操作、重新连接。

  B. 原生执行
     - 通过官方 UserService 执行有限时长的 Android shell 命令。
     - 返回标准输出、标准错误、退出码、截断标记及实际耗时。
     - 操作 ID、作用域、重复请求识别、并发上限和执行前身份检查。
     - 取消与超时传递到实际进程；处理 Binder 死亡及服务重启。
     - 原生控制器独立于 Flutter 页面生命周期。

  C. 聊天接入
     - 首先支持应用管理的内置 OpenCode V2。
     - 注册独立 Shizuku 工具，并经过现有工具权限体系。
     - 工具结果明确标注 Android ADB/ROOT 环境。
     - 纳入现有工具过程卡和任务关联，不新增模型循环。
     - 关闭能力后，已缓存的工具定义也不能继续执行新命令。

  D. 诊断与恢复
     - 清楚说明未安装、未启动、未授权、版本不支持和服务失联。
     - 重连后对账在途 operationID，结果不确定时保留 unknown。
     - 通过真实只读命令验证链路，不能只检查开关或模拟数据。

2.2 首版界限

  - 主链是有限时长的前台命令，不把任意后台守护进程作为已支持能力。
  - 包管理、appops、settings 等可由获准的命令工具执行；专用操作面板后续补。
  - Accessibility、输入法、屏幕自动化、NFC 和工作流不列入此版验收。
  - 远端 OpenCode 控制手机要另做设备配对与中继，不使用远端的 127.0.0.1 冒充手机。
  - 其他 agent 的 MCP 接入留待适配，不默认它们与 V2 插件拥有相同上下文能力。
  - Sui 若由官方 Provider 自动发现，准确显示其身份；专项兼容验证单列。


三、已核验的事实与附件修正
==========================

3.1 官方依赖

  截至本次读取，Maven Central 的 api 元数据把 13.1.5 标为 latest/release。
  拟锁定：
    dev.rikka.shizuku:api:13.1.5
    dev.rikka.shizuku:provider:13.1.5

  Shizuku-API 仓库 LICENSE 为 MIT，Copyright (c) 2021 RikkaW。
  实施时再核对锁定工件的 POM、依赖树与许可证，写入现有第三方说明。
  本应用使用 SDK，不捆绑 Shizuku 管理器，不复用其启动图标。

3.2 Provider 和权限

  官方文档要求注册 rikka.shizuku.ShizukuProvider：
    authority：${applicationId}.shizuku
    exported：true
    multiprocess：false
    permission：android.permission.INTERACT_ACROSS_USERS_FULL

  该 permission 用于保护 Provider，不是申请让本应用获得跨用户系统权限。
  API 权限申请使用 Shizuku 自己的监听和 requestPermission 流程。
  管理器是否安装、Binder 是否可达、应用是否获授权是三件事。
  Sui 路径下可能没有 Shizuku 管理器安装，不能据此判定后端不可用。

3.3 身份

  Shizuku.getUid()：0 表示 ROOT，2000 表示 ADB shell。
  其他值或查询失败显示未知/不支持，不推断成 ROOT。
  getSELinuxContext() 作为可选真实字段，取不到保持空值。
  ADB 权限受系统版本、OEM 和 SELinux 影响；不承诺它可访问其他应用私有数据。

3.4 UserService

  使用 bindUserService，不采用已弃用的 newProcess 路线。
  UserService 是独立特权进程中的 Binder 对象，不是普通 Android Service。
  不能依赖其中的 Context 像普通应用那样注册接收器或访问所有内容服务。

  UserServiceArgs 显式指定：
    - 稳定 tag；需要区分应用包和 Android 用户。
    - serviceVersion；服务实现改变时更新，不能只在协议改变时更新。
    - daemon(false)；调用应用进程死亡时由框架管理该非守护服务。
    - 独立 processNameSuffix。

  协议版本、服务代码版本、服务实例 ID 分开：
    协议版本决定报文兼容；
    服务版本决定升级后是否替换旧实现；
    实例 ID 决定某次响应是否来自仍然有效的进程。

3.5 取消和 destroy 的区别

  附件把单次取消与 destroy 链路绑定得过紧，需要调整。
  正常取消：停止指定 operationID 对应的命令进程及可确认归属的子进程。
  destroy：清理并关闭整个 UserService，用于停用、退出清理和版本替换。

  官方规定的 destroy transaction：
    AIDL 显式方法编号为 16777114；实际 Binder transaction code 为 16777115。
  关闭服务先清理其拥有的命令，再结束 UserService 进程。
  服务关闭或 Binder 死亡不能直接证明之前的命令没有产生副作用。

3.6 非 SDK API

  官方文档说明 UserService 进程不受普通应用的 hidden API 限制。
  首版使用 UserService + shell，不需要为了接入而额外安装 HiddenApiBypass。
  只有未来在主应用进程中直接调用受限系统接口时，才评估额外依赖。

3.7 非 root 设备重启

  系统重启后，非 root 的 Shizuku 通常需要用户重新启动。
  Android 11 起可通过无线调试在手机上启动；更早版本通常需要电脑 ADB。
  App 提供状态和管理器入口，不把“打开管理器”描述成“已自动启动”。

3.8 附件中的许可说法需要区分

  “实现相同功能就必然构成 AGPL 衍生作品”过于绝对。
  独立实现功能与复制受保护的代码表达是不同问题。
  MIT 与 AGPL 也不是绝对不能组合；直接复用时，组合发行需满足适用的 AGPL 条款，
  不能仅凭当前项目写了 MIT 就免除这些义务。
  使用独立进程或 HTTP 也不是自动免除许可义务的保证。

  本模块采用明确路线：官方 Shizuku-API + Android 平台文档 + 本项目独立实现。
  后续已按用户要求阅读 rikkahub-agent 的调用架构、AIDL、行为测试和议题以审计故障。
  新代码基于官方 SDK/平台文档独立编写，不复制该 AGPL 仓库的代码、AIDL、测试或提示词。
  保留官方依赖来源、版本和许可证记录；不能将这次对照审计称为严格洁净室。


四、架构及责任划分
==================

4.1 调用链

  Flutter 设置 / 聊天
     -> domain/state
     -> Native Shizuku Controller / 最小设备操作代理
     -> Shizuku Binder
     -> 应用自有 UserService
     -> Android shell 命令

  内置 OpenCode
     -> 应用自有 V2 插件
     -> 已认证的本机桥
     -> 同一个设备操作代理
     -> 同一个 UserService。

4.2 责任

  Dart domain：状态、显示数据、操作作用域和错误码。
  Dart state/platform：设置操作、原生通道、生命周期订阅。
  Kotlin controller：Binder 监听、权限、绑定、服务实例、设备状态。
  操作代理：操作领取、作用域核对、状态持久化、取消、结果查询。
  UserService：真实身份核验、命令执行、输出读取、进程停止。
  V2 插件：从上下文取得会话身份、工具权限、向设备桥调用、传播取消。

4.3 生命周期

  控制器由 application 范围持有，页面只订阅状态。
  页面销毁仅移除订阅，不能误杀其他会话仍在执行的命令。
  实际运行任务使用已有工作租约和后台宿主；不增加无条件常驻服务。
  关闭 Shizuku 功能时拒绝新命令，处理在途命令，然后释放本模块资源。
  用户明确停止全部后台运行时，该模块也必须停止。
  普通页面返回、Activity 重建和用户明确退出必须有不同处理。

4.4 本机桥

  优先在当前原生生命周期内提供小型 loopback 桥，绑定 127.0.0.1 随机端口。
  只提供本模块所需的 status、submit、result、cancel 协议。
  端口/短期凭证经应用私有文件或私有 IPC 交给内置运行时。
  不把桥凭证交给模型，不放到工具参数、聊天消息或诊断日志。
  明确限制请求大小、输出大小、连接数和请求期限。

  启用此传输前先验证：
    应用进程恢复后是否更新端口/凭证；
    Ubuntu 与 Android 私有路径的映射；
    远端服务器不会被误识别为内置运行时；
    缺少原生宿主时返回不可用，不启动替代执行环境。

  本机桥是访问控制，不是抵御同 UID 任意执行的安全沙箱。
  若实现阶段发现稳定性问题，应先解决传输验证，再增加命令工具，不临时绕过。


五、协议草案
============

以下字段和操作名是本项目拟建协议，不是 Shizuku 官方 API，也不是已经存在的接口。
SHZ-001 完成后冻结为 schema，并用它驱动 Dart/Kotlin/插件之间的契约测试。

5.1 状态快照

  protocolVersion：1。
  brokerInstance：本次操作代理实例 ID。
  serviceInstance：当前 UserService 实例 ID；未连接时为空。
  managerInstalled：true/false/unknown。
  binderAlive：true/false。
  serverVersion：实际读数或空。
  permission：unknown / denied / requestable / granted。
  enabled：用户对本模块的独立开关。
  binding：disconnected / connecting / connected / failed。
  uid：实际 UID 或空。
  backend：adb / root / unknown。
  selinuxContext：实际值或空。
  compatibility：supported / unsupported / unknown。
  observedAt：设备采集时间。

5.2 提交命令

  protocolVersion、brokerInstance、operationID。
  source：settings_test 或 opencode_tool。
  scope：serverIdentity、location、sessionID、toolCallID、agentID。
  expectedServiceInstance、expectedUid。
  command、timeoutMs、outputLimitBytes。

  scope 由受信任的调用适配器根据执行上下文填入，不接受模型指定身份。
  设置页诊断使用独立本地 scope，不伪造用户会话或模型调用。
  用户选择的任务身份沿用现有 admission 元数据，未知关联保持待关联。

5.3 操作结果

  operationID、serviceInstance、uid。
  state：queued / waiting / running / succeeded / failed / cancelled / unknown。
  reason：有限错误码或等待原因。
  acceptedAt、startedAt、finishedAt：未知时为空。
  elapsedMs：执行器单调时钟测量，不能由服务器与手机跨时钟相减。
  exitCode：只有取得真实退出码才填写。
  stdout、stderr、truncated。
  termination：not_requested / requested / confirmed / unconfirmed。

  退出码 0 才表示命令正常结束；输出中写着“success”不能覆盖退出状态。
  cancelled 说明已确认终止执行，不表示命令产生的所有副作用已回滚。

5.4 推荐的首版资源界限

  - 同一手机同时执行 1 条 Shizuku 命令。
  - 忙时返回 busy；不先引入可能无限增长的后台命令队列。
  - 默认超时 30 秒，可配置范围建议 1—120 秒。
  - 命令 UTF-8 上限建议 16 KiB。
  - stdout/stderr 合计返回上限建议 64 KiB。
  - 到达输出上限后继续排空管道并标记截断，避免子进程因管道阻塞而挂住。
  - 这些是初始设计值，协议冻结前结合 Binder/HTTP 开销核验。

5.5 必须覆盖的报文情形

  正常提交：
    同一调用上下文生成 operationID，返回 accepted；之后查询到 running 和最终结果。

  重复提交：
    相同 operationID、scope 和参数摘要返回已有记录；不能再启动命令。
    相同 ID 但参数或作用域不同，返回 conflict。

  取消：
    cancel 指定 operationID 和拥有者；返回取消请求已受理。
    只有执行器确认进程结束，才返回 confirmed/cancelled。

  超时晚回：
    客户端超时后不创建新 ID 重发。
    晚到的结果仍写入原 operationID，UI 可查询核对。

  旧实例响应：
    服务实例改变后，旧实例结果只能更新其原操作历史，不能满足新命令。
    旧能力快照不能在新 UID 下直接执行。


六、持久化、unknown 与恢复
==========================

6.1 存储分工

  控制记录：操作 ID、拥有者、参数摘要、服务实例、状态和时间。
  临时输出：有界、应用私有，仅供当前操作结果查看；制定清理策略。
  展示历史：可裁剪的近期操作列表。
  去重记录：与展示历史分开，裁剪列表不能让相同请求重新执行。

  不把完整命令/输出写进 mobile-insights 或普通诊断日志。
  正常工具消息里保留向用户返回的命令结果，遵循现有会话存储行为。
  SDK 许可记录和协议版本随代码提交；桥凭证不进入仓库或导出包。

6.2 对账触发时机

  - App 冷启动。
  - Binder 死亡或重新收到 Binder。
  - UserService 重连或版本替换。
  - OpenCode 插件重载/重新连接。
  - 用户点击“刷新操作结果”。

6.3 对账规则

  查询本机尚未终结的 operationID，按原 serviceInstance 获取事实。
  同一实例仍执行：恢复 running，提供停止。
  原实例存在且已有结果：补齐最终状态。
  原实例已消失，且没有可靠完成记录：unknown，显示“执行结果未确认”。
  收到可信晚回：只更新原记录，不重新执行。
  无法确认外部副作用：不自动重试；用户再次执行会产生明确的新操作。

6.4 向前恢复

  新增存储带 schemaVersion，升级前保留可恢复副本或采用原子迁移。
  无法解析的记录不得被空列表覆盖；禁用执行并显示存储错误。
  停用功能后旧操作可读、可按策略清理，未确认记录不会自动恢复运行。
  明确提供清理本模块数据的入口，不连带删除 Ubuntu、项目或已有服务器凭据。


七、命令执行与取消实现约束
==========================

7.1 执行前

  重新核对 enabled、授权、Binder、服务实例、实际 UID、作用域和超时范围。
  在不可逆的启动边界前写入领取记录。
  接到取消或实例过期时，不启动新的命令进程。

7.2 执行中

  通过 Android 的 shell 环境执行，明确工作目录及可用 PATH。
  不把 Ubuntu 的 /root/projects 路径当成 Android shell 的同名目录。
  并发读取 stdout/stderr，限制结果大小并持续排空。
  记录 PID、进程组和可验证的进程实例身份。
  禁止用宽泛进程名匹配方式终止命令。

7.3 取消和超时

  首先终止明确归属的命令进程组，等待短暂清理，再按需强制终止。
  进程组启动/管理方式需在目标 Android 系统验证，不能只假定某个 shell 工具存在。
  Binder 取消线程不能被执行线程的长时间阻塞占住。
  对自行 daemonize、脱离进程组的任意命令，不能保证“杀掉 shell 就杀掉全部后代”。
  无法证明全部执行已结束时返回 unconfirmed/unknown，不虚报已全部取消。

7.4 关闭 UserService

  destroy 先拒绝新操作，再停止当前归属任务、关闭管道与资源，最后退出。
  daemon(false) 与明确清理配合使用，不依赖 Activity.onDestroy 充当进程退出通知。
  Android 杀进程时通常没有可靠 onDestroy，恢复依赖下一次启动对账。

7.5 权限撤销

  Shizuku API 的权限查询可能有客户端缓存；不能把单次 granted 快照当永久授权。
  捕获服务端权限异常、Binder 状态变化并及时清除本模块就绪状态。
  实际撤销权限时是否中止已绑定 UserService，列入真机专项测试。
  不能用“申请过权限”作为后续执行的唯一依据。

十、验收清单
============

T01 未安装管理器、无 Sui：准确显示未就绪，并能打开官方安装说明。
T02 已安装但未启动：显示未运行，点击管理器入口不伪报启动成功。
T03 拒绝授权：保持禁用；允许授权后，功能仍等待用户单独启用。
T04 ADB 模式：显示 UID 2000；id 的真实输出与执行结果一致。
T05 ROOT 模式：仅在实际有 root 测试设备时验收；否则标待验证。
T06 版本读取：getprop 输出来自 Android，不是 Ubuntu 的系统信息。
T07 非零退出：返回真实 exitCode，不因存在输出而显示成功。
T08 大输出：截断标记正确，stdout/stderr 不导致死锁或无界内存。
T09 取消：实际终止测试命令及可确认归属的后代；UI 和原生结果一致。
T10 超时：不重复执行，晚回更新原操作，未确认结果保持 unknown。
T11 Shizuku 重启：旧操作不自动重发，新实例经过验证后可执行新操作。
T12 身份切换：ADB -> ROOT 或反向切换后，旧能力快照不能直接复用。
T13 权限撤销：执行前/执行中分别验证，不能依赖缓存授权无限继续运行。
T14 页面关闭与旋转：不丢操作归属，不把界面销毁当作成功完成。
T15 App 进程终止：恢复后对账，没有记录的结果不猜成功或失败。
T16 两个会话同时调用：按 busy 策略处理，不混输出和取消目标。
T17 相同 ID 重复请求：只执行一次；改参数复用 ID 返回 conflict。
T18 远端服务器：明确不支持本机 Shizuku；不能错误连接远端 loopback。
T19 关闭开关：后续调用立即拒绝，已缓存工具也不能绕过。
T20 升级：UserService 代码版本变化触发替换，旧实例操作保持可查。
T21 预览包：Provider authority 与服务 tag 不与正式包串用。
T22 文案与主题：中英、浅深色、大字号符合当前 Kit 风格。
T23 记录：普通日志和 insights 不含命令正文、输出或桥凭证。
T24 回归：原有搜索、任务、聊天、密钥、记忆、终端不因模块关闭而受影响。

测试条件说明：
  - 当前环境在手机内置 Ubuntu，没有 adb 连接到宿主手机。
  - 原生特殊权限/服务生命周期不能只靠本环境 shell 验证。
  - 完整 Flutter/Gradle 构建优先走 CI，真机由安装测试 APK 后验证。
  - Android 8/10/13/16 等兼容性按实际设备或测试设施覆盖，不声明未测版本全通过。
  - CI 通过与“用户手机上已授权且成功执行”分别报告。
